# Parts Catalog

Веб-каталог, синхронизируемый с товарами бренда Omegation продавца на **Ozon**. Публичная витрина показывает товары с возможностью поиска по названию, артикулу и номеру детали/аналога. Синхронизация сохраняет в базу только товары бренда Omegation — остальной ассортимент продавца на Ozon в базу не попадает и, соответственно, не виден нигде, включая админ-панель (см. «Атрибуты Ozon и их роль в каталоге»). Отдельная админ-панель позволяет редактировать контент карточек (фото, описание) без потери данных при следующей синхронизации.

## Архитектура

Проект состоит из четырёх контейнеров, поднимаемых через `docker-compose.yml`:

| Сервис | Назначение |
|---|---|
| `db` | PostgreSQL 16 — хранит каталог товаров, изображения, атрибуты, остатки, журнал синхронизаций и аудит действий админа |
| `api` | FastAPI-приложение — публичное и админское REST API |
| `sync_worker` | Отдельный процесс (`scheduler.py`), периодически подтягивающий данные из Ozon Seller API и обновляющий БД |
| `nginx` | Отдаёт собранный React-фронтенд (статика) и проксирует запросы к `api`, а также раздаёт загруженные вручную изображения |

Схема данных: Ozon → `sync_worker` (по расписанию) → PostgreSQL → `api` → фронтенд. Админ может через свою панель точечно переопределять контент (фото, описание) — эти изменения помечаются флагом `manual_override` и не затираются следующей синхронизацией, если админ явно не откатит их назад через "Revert to sync".

## Стек технологий

**Backend**
- Python, FastAPI, Uvicorn
- SQLAlchemy 2.0 + PostgreSQL (`psycopg2-binary`)
- APScheduler — периодический запуск синхронизации с Ozon
- `ozonapi-async` — клиент Ozon Seller API
- `python-multipart` — загрузка изображений через админку

**Frontend**
- React + Vite
- MUI (Material UI) — компоненты интерфейса
- React Router — маршрутизация
- Светлая/тёмная тема с сохранением выбора в `localStorage`

**Инфраструктура**
- Docker Compose (4 сервиса)
- Nginx — реверс-прокси и раздача статики

## Переменные окружения

Скопируйте шаблон и заполните реальными значениями:

```bash
cp .env.example .env
chmod 600 .env
```

| Переменная | Назначение |
|---|---|
| `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` | Подключение к PostgreSQL. `DB_HOST=db` — имя сервиса в Docker-сети |
| `OZON_CLIENT_ID`, `OZON_API_KEY` | Read-only ключ Ozon Seller API для синхронизации товаров |
| `APP_ENV` | Режим приложения (`production` скрывает `/docs`/`/redoc`/`/openapi.json`; `development` — оставляет их видимыми, удобно на тестовом стенде) |
| `SYNC_INTERVAL_MINUTES` | Периодичность запуска синхронизации с Ozon, в минутах (по умолчанию 60) |
| `UPLOAD_DIR` | Путь внутри контейнера для изображений, загруженных вручную через админку (`/app/uploads`) |
| `ADMIN_URL_UID` | **Обязательно.** Секретная часть адреса админки `/console/<uid>/login` (24–64 символа; `openssl rand -hex 24`). Не задан — админка закрыта |
| `SESSION_ABSOLUTE_HOURS`, `SESSION_IDLE_MINUTES`, `MAX_SESSIONS_PER_USER` | Срок и число сессий админки (12 / 120 / 5) |
| `LOGIN_WINDOW_MINUTES`, `LOGIN_MAX_FAILS_PER_IP`, `LOGIN_MAX_FAILS_PER_USER` | Блокировка перебора пароля (15 / 10 / 10) |
| `OUTBOUND_ALLOW_PRIVATE` | `1` — разрешить FTP-серверы во внутренней сети (по умолчанию запрещено) |
| `FTP_UPLOAD_USER`, `FTP_UPLOAD_PASSWORD`, `FTP_PUBLIC_IP`, `FTP_PASV_PORTS` | Встроенный FTP-сервер для прайсов (см. раздел «Безопасность» в конце) |

Доступ к админ-панели больше не переменная окружения — см. раздел
[«Авторизация»](#авторизация) ниже: именные учётные записи с ролями,
создаются через `manage_users.py` или саму админку.

⚠️ **Не коммитьте `.env` в репозиторий** — он уже добавлен в `.gitignore`. Храните ключи Ozon в секрете.

## Быстрый старт (Docker Compose)

```bash
git clone <repo_url> parts-catalog
cd parts-catalog

cp .env.example .env
# заполните .env реальными значениями (см. таблицу выше)
chmod 600 .env

# Собрать фронтенд перед первым запуском
cd frontend
npm install
npm run build
cd ..

docker compose up -d --build
```

После старта:
- Публичный каталог — `http://<host>/`
- Админ-панель — `https://<host>/console/<ADMIN_URL_UID>/login` (секретный адрес, см. раздел «Безопасность» в конце)
- Проверка статуса синхронизации — `GET /sync/status`

Проверить, что все сервисы поднялись:

```bash
docker compose ps
docker compose logs -f api
docker compose logs -f sync_worker
```

**Первый вход в админку.** Учётных записей ещё нет — создайте первую (роль
`full`) из контейнера `api`:

```bash
docker compose exec api python manage_users.py create-user admin --role full
```

Скрипт спросит пароль дважды (не короче 8 символов) и создаст пользователя.
Дальше можно войти на `/console/<ADMIN_URL_UID>/login` под этим логином/паролем — подробнее
см. [«Авторизация»](#авторизация).

## Авторизация

Доступ к `/admin/*` — именные учётные записи с ролями вместо одного общего
токена на всех. Роли, по возрастанию прав:

| Роль | Уровень доступа |
|---|---|
| `viewer` | Только просмотр: каталог в админке, карточки товаров, история синхронизации и настройки сайта — без права их менять |
| `editor` | `viewer` + редактирование карточек товаров: контент (название/описание/бренд/категория), фото, откат ручных правок (revert-to-sync) |
| `full` | `editor` + всё, что меняет общие данные сайта целиком: настройки сайта (шапка/о нас/контакты), настройки и запуск синхронизации (Ozon и FTP), управление пользователями |

Сессия выдаётся при входе (`POST /admin/auth/login`) — случайный токен,
которым фронтенд подписывает дальнейшие запросы (`Authorization: Bearer
<token>`), как раньше с `ADMIN_TOKEN`, только именной и отзываемый. На
сервере хранится не сам токен, а его SHA-256-хеш — восстановить токен из
БД нельзя. Сессия живёт до 12 ч (простой — 2 ч; настраивается в `.env`) или до выхода (`POST /admin/auth/logout`)
/ деактивации пользователя, что отзывает её мгновенно.

Пароли хранятся как `PBKDF2-HMAC-SHA256` (только стандартная библиотека
Python — без `bcrypt`/`passlib` и их нативной сборки в Docker).

### Управление пользователями

Через саму админку (раздел «Пользователи», виден только роли `full`) —
создание, смена роли, отключение/включение, сброс пароля.

Либо из командной строки, тем же скриптом, которым создаётся самая первая
учётная запись (нужен доступ к контейнеру `api`, например по SSH на
сервер):

```bash
docker compose exec api python manage_users.py create-user <логин> --role viewer|editor|full
docker compose exec api python manage_users.py list-users
docker compose exec api python manage_users.py set-password <логин>
docker compose exec api python manage_users.py set-role <логин> editor
docker compose exec api python manage_users.py deactivate <логин>
docker compose exec api python manage_users.py activate <логин>
```

### Auth-эндпоинты

| Метод | Путь | Описание |
|---|---|---|
| POST | `/admin/auth/login` | `{username, password}` → `{token, user}`. Без авторизации |
| POST | `/admin/auth/logout` | Отзывает текущую сессию |
| GET | `/admin/auth/me` | Текущий пользователь (`id`, `username`, `role`) |
| GET | `/console/<uid>/users` | Список пользователей (роль `full`) |
| POST | `/console/<uid>/users` | Создать пользователя: `{username, password, role}` (роль `full`) |
| PATCH | `/admin/users/{id}` | Изменить роль/статус/пароль: `{role?, is_active?, password?}` (роль `full`). Нельзя отключить или понизить с `full` собственную учётную запись |

## Синхронизация с Ozon

Сервис `sync_worker` запускает `scheduler.py`, который каждую минуту опрашивает
таблицу `sync_settings` (управляется из админки, раздел **Синхронизация**,
`/admin/sync`) и запускает синхронизацию, когда пришло время по заданному в
ней интервалу. При каждом запуске синхронизация:

1. Обращается к Ozon Seller API (`OZON_CLIENT_ID` + `OZON_API_KEY`) за списком товаров и их атрибутами.
2. Обновляет/создаёт записи `Part`, `PartImage`, `PartAttribute`, `PartStock` в PostgreSQL — данные (цена, остатки, атрибуты, название) обновляются всегда.
3. Если в настройках включено скачивание фото (по умолчанию — да), скачивает фото карточек с CDN Ozon на сервер (`UPLOAD_DIR`) и обновляет `part.primary_image`/галерею `PartImage`. Если выключено — этот шаг полностью пропускается, фото не трогаются.
4. Пишет результат каждого запуска в `SyncLog`: успех/ошибка, число обработанных и упавших товаров, число скачанных/не скачанных/пропущенных фото.
5. **Не перезаписывает** карточки, которые админ вручную отредактировал (`manual_override = true`) — такие товары обновляются только по остаткам/цене, но не по фото и описанию, пока админ не сделает "Revert to sync".

`SYNC_INTERVAL_MINUTES` в `.env` используется только как значение по
умолчанию при самом первом запуске (пока в БД ещё нет строки настроек) —
дальше интервал и вкл/выкл автосинхронизации живут в БД и правятся из
админки без перезапуска контейнеров.

### Раздел «Синхронизация» в админке (`/console/<uid>/sync`)

Три блока:

**Самопроверка** — кнопка «Проверить всё»: БД доступна, заданы ли ключи Ozon
в `.env`, доступна ли на запись папка загрузок фото, отвечает ли FTP (если
включён), успешна ли была последняя синхронизация с Ozon.

**Товары и фото (Ozon)** — как и раньше: статус, время последнего/следующего
запуска, число обработанных товаров и скачанных/не скачанных фото, история
запусков, настройки (периодичность, вкл/выкл автосинхронизации, вкл/выкл
скачивания фото), кнопка «Запустить сейчас» (с опцией «только данные, без
фото»).

**Цены с FTP** — импорт цен из таблицы (CSV или XLS/XLSX, две колонки:
артикул и цена) с внешнего FTP-сервера. Артикул сопоставляется с `offer_id`
товара. Цена из FTP **приоритетнее** цены Ozon: как только для товара
находится совпадение, `part.price` перестаёт обновляться обычной
синхронизацией с Ozon — до тех пор, пока товар не пропадёт из файла на FTP
при одном из следующих импортов (тогда приоритет снимается автоматически).
Работает по собственному расписанию, независимому от интервала синхронизации
с Ozon. В блоке — те же статус/история/настройки, что и у Ozon-синхронизации,
плюс:
- адрес/порт/логин/пароль/путь к файлу/FTPS — всё настраивается прямо в
  админке (пароль при показе всегда замаскирован, вводится заново только при
  смене);
- кнопка «Проверить соединение» — быстрый селфчек конкретно FTP: подключается
  и проверяет, что файл виден и доступен, ничего не скачивая и не импортируя;
- кнопка «Импортировать сейчас» — ручной внеочередной запуск;
- в истории по каждому запуску — сколько артикулов сопоставилось и сколько не
  нашлось (с примерами, чтобы быстро найти ошибку в файле или в выгрузке).

Backend-эндпоинты (требуют `Authorization: Bearer <token>` сессии — см.
[«Авторизация»](#авторизация); минимальная роль указана в скобках):

| Метод | Путь | Описание |
|---|---|---|
| GET | `/admin/sync/status` (`viewer`) | `{ozon: {...}, ftp: {...}, settings: {...}}` — статус и время следующего запуска для каждого источника отдельно |
| GET | `/admin/sync/history?source=ozon\|ftp&limit=20` (`viewer`) | История запусков; без `source` — общая лента обоих |
| GET | `/admin/sync/settings` (`viewer`) | Текущие настройки (пароль FTP не отдаётся, только `ftp_password_set: bool`) |
| PUT | `/admin/sync/settings` (`full`) | Частичное обновление любых полей (Ozon и/или FTP); пустой `ftp_password` не затирает сохранённый |
| POST | `/admin/sync/run` (`full`) | Синхронизация с Ozon сейчас; тело `{"download_images": true\|false\|null}` |
| POST | `/admin/sync/run-ftp` (`full`) | Импорт цен с FTP сейчас |
| POST | `/admin/sync/ftp/test` (`full`) | Проверка FTP-соединения без импорта; поля необязательны — что не передано, берётся из сохранённых настроек |
| GET | `/admin/sync/selfcheck` (`viewer`) | Общая самопроверка (см. выше) |

Упрощённый публичный статус синхронизации с Ozon (без токена, без деталей по фото/FTP) остался как был:

```

```

```

## Атрибуты Ozon и их роль в каталоге

Ozon хранит характеристики товара в виде списка `{id, value}`. В проекте используются три атрибута с особой ролью:

| ID атрибута | Назначение |
|---|---|
| **85** | Название бренда. Товар сохраняется в БД, только если значение этого атрибута содержит "Omegation" (без учёта регистра, см. `catalog_rules.is_omegation_brand`) — остальные бренды из общего Ozon-каталога продавца в базу вообще не попадают, значит не видны нигде, включая админ-панель |
| **9048** | Номер детали / артикул аналога. Используется как **основной отображаемый артикул** товара (поле `article` в API) и участвует в дополнительном поиске — так покупатель может найти товар по номеру детали, даже если он не совпадает с внутренним `offer_id` |
| ~~4191~~ | Ранее входил в список отображаемых характеристик, **исключён** — не несёт полезной информации для покупателя |

Фильтр по бренду применяется на **записи**, в синхронизации (`sync_ozon.py`,
`app/catalog_rules.py`), а не только на чтении: у товара, для которого Ozon
не вернул атрибут 85 со значением "Omegation", карточка не создаётся, а
существующая (например, оставшаяся с более раннего запуска, до появления
этого фильтра) — удаляется при следующей синхронизации. Число пропущенных
и удалённых так карточек видно в истории синхронизации на `/admin/sync`
(поля `skipped_other_brand` / `removed_other_brand` в `SyncLog.details`).

В карточке товара (`GET /parts/{id}` → `attributes`) показываются только атрибуты **85** и **9048** — остальные технические атрибуты Ozon (цены модерации, статусы, промо и т.д.) отфильтрованы на backend и никогда не попадают в ответ API.

Если у товара не заполнен атрибут 9048, поле `article` автоматически подставляет `offer_id` как запасной вариант.

| GET | `/parts` | Список товаров бренда Omegation. Параметры: `search`, `in_stock_only`, `page`, `page_size` |
| GET | `/parts/{id}` | Полная карточка товара: фото, описание, характеристики (85, 9048), остатки по складам |
| GET | `/images/{uid}` | Постоянный адрес фото (снаружи — `/api/images/{uid}`), отдаёт текущий файл фото; см. «Постоянные адреса фото» ниже |
| GET | `/brands` | Список брендов, присутствующих в каталоге (справочно) |
| GET | `/sync/status` | Статус последнего запуска синхронизации с Ozon |

**Поиск (`/parts?search=...`)** ищет одновременно по:
- названию товара,
- `offer_id` (внутреннему артикулу),
- OEM-номерам из атрибута 9048 (номер детали/аналоги, через «; »).

Артикул и OEM-номера сравниваются нормализованно — без учёта регистра, пробелов,
дефисов, точек и слэшей, а также с приставкой/суффиксом `-omg` и без него:
запросы `0155305363`, `0155-305-363` и `0155305363-omg` находят один и тот же
товар. Точное совпадение с артикулом или с одним из OEM-номеров показывается
выше простого вхождения в строку.

**Постоянные адреса фото.** У каждого фото в карточке есть неизменный `uid`;
адрес `/api/images/{uid}` не меняется, даже если сам файл заменили — из админки
(кнопка «Заменить файл» на фото) или на Ozon (при синхронизации фото на той же
позиции подменяется «под тем же uid»). Старые прямые ссылки `/uploads/<файл>`
продолжают открываться. Для фото, добавленного по внешней ссылке, постоянный
адрес перенаправляет (302) на эту ссылку.

## Админ API

Все эндпоинты `/admin/*` защищены ролевой авторизацией (`admin_auth.py`,
`require_viewer`/`require_editor`/`require_full`) — см. раздел
[«Авторизация»](#авторизация). Показывает весь синхронизированный
каталог — а это и есть только товары Omegation, поскольку синхронизация не
сохраняет в БД остальной ассортимент продавца на Ozon (см. «Атрибуты Ozon и
их роль в каталоге»). Минимальная роль указана в скобках.

| Метод | Путь | Описание |
|---|---|---|
| GET | `/admin/parts` (`viewer`) | Список синхронизированного каталога. Параметры: `search`, `only_edited`, `page`, `page_size` |
| GET | `/admin/parts/{id}` (`viewer`) | Полная карточка товара для редактирования |
| PATCH | `/admin/parts/{id}` (`editor`) | Изменить контент (название, описание и т.д.) — выставляет `manual_override = true` |
| POST | `/admin/parts/{id}/revert-to-sync` (`editor`) | Откатить ручные правки, вернуть карточку под управление синхронизации |
| POST | `/admin/parts/{id}/images/upload` (`editor`) | Загрузить изображение файлом (JPEG/PNG/WEBP, до 10 МБ) |
| POST | `/admin/parts/{id}/images/{uid}/replace` (`editor`) | Заменить файл у существующего фото — `uid` и публичный адрес не меняются |
| POST | `/admin/parts/{id}/images/by-url` (`editor`) | Добавить изображение по внешней ссылке |
| DELETE | `/admin/parts/{id}/images` (`editor`) | Удалить изображение (`?image_url=...`) |
| PUT | `/admin/parts/{id}/images/reorder` (`editor`) | Изменить порядок и главное изображение |
| GET | `/admin/parts/{id}/audit-log` (`viewer`) | Журнал всех ручных изменений по товару |
| GET | `/admin/settings` (`viewer`) | Текущий контент сайта (шапка/о нас/контакты) |
| PUT | `/admin/settings` (`full`) | Сохранить контент сайта |

Каждое админское изменение фиксируется в таблице `AdminAuditLog` (кто/что/когда изменил) — доступно через `audit-log`.

Ниже — что было закрыто автоматически кодом/конфигом, и что требует одного

### Уже работает само (просто пересобери контейнеры)

- **Rate limiting** — 120 запросов/минуту с одного IP на все эндпоинты
  (`slowapi`). Защита от скрейпинга каталога и перебора admin-токена.
- **Непривилегированный пользователь в контейнере** `api`/`sync_worker`
  вместо root.
- **Лимиты памяти/CPU** на все контейнеры в `docker-compose.yml`.
- **Health-check** у `api` и `nginx` (не только у `db`, как раньше).
- **Локальная заглушка** для товаров без фото вместо внешнего
  `via.placeholder.com`.
- **`/docs`, `/redoc`, `/openapi.json` скрыты** при `APP_ENV=production`
  (уже стоит по умолчанию в `.env.example`).

### Требует одного ручного шага

**1. Миграции БД (Alembic) — для уже существующей базы:**

У тебя база уже создана через `Base.metadata.create_all()`. Если запустить
`alembic upgrade head` как есть — Alembic попробует создать те же таблицы
заново и упадёт с ошибкой. Нужно один раз "подружить" Alembic с уже
существующей базой, не трогая данные:

```
docker compose exec api alembic stamp 0001
```

Это просто помечает базу как уже находящуюся на начальной ревизии, ничего
не создаёт и не удаляет. После этого шага для **новых** изменений схемы
(если я в будущем добавлю поле в модель) — вместо того чтобы просто менять
`models.py`, будет создаваться файл миграции, и применяется он так:

```
docker compose exec api alembic upgrade head
```

Для **нового** (пустого) деплоя на другом сервере — то же самое сработает
через `alembic upgrade head` с нуля, `create_all()` тоже подстрахует
(идемпотентен, ничего не сломает, если таблицы уже есть).

**2. Бэкапы базы данных:**

```
chmod +x backup.sh
./backup.sh          # ручной запуск, проверить что работает
crontab -e
```

Добавить строку (бэкап каждую ночь в 3:30):
```
30 3 * * * /home/xxx/parts-catalog-main/backup.sh >> /home/xxx/parts-catalog-main/backups/backup.log 2>&1
```

Бэкапы копятся в `./backups/parts_catalog_*.sql.gz`, хранятся 14 дней.
**Важно:** периодически скачивай их с сервера (scp/rclone) — бэкап на том
же диске, что и сама база, не спасёт при отказе всего сервера.

Восстановление из бэкапа:
```
gunzip < backups/parts_catalog_ДАТА.sql.gz | docker compose exec -T db psql -U parts_app -d parts_catalog
```

**3. HTTPS для домена omegation.ru:**

Убедись, что A-запись `omegation.ru` уже указывает на IP этого сервера
(проверить: `dig +short omegation.ru` — должен вернуть IP сервера), затем:

```
docker compose up -d
docker compose run --rm certbot certonly --webroot -w /var/www/certbot \
  -d omegation.ru --email твой@email.ru --agree-tos --no-eff-email
```

Замени `твой@email.ru` на свою почту — Let's Encrypt шлёт туда уведомления
об истечении сертификата (страховка на случай, если автопродление
почему-то не сработает).

После успешного выпуска:
```
cp nginx/nginx-ssl-example.conf nginx/nginx.conf
docker compose restart nginx
```

Сертификат обновляется автоматически — сервис `certbot` в
`docker-compose.yml` сам проверяет и продлевает его раз в 12 часов.

Если позже понадобится ещё и `www.omegation.ru` — добавь `-d www.omegation.ru`
в команду certbot выше и `www.omegation.ru` в `server_name` в обоих nginx-конфигах
(но только если для www тоже настроена A/CNAME-запись, иначе certbot не
сможет подтвердить домен и упадёт с ошибкой).

## Обновление 2026-09-28: фикс падения nginx + раздел «Синхронизация»

**1. Фикс `nginx: host not found in upstream "api"` (краш-луп на проде).**

Причина: `nginx` в `docker-compose.yml` был указан как зависящий от `api`
через обычный `depends_on: [api]`, который ждёт только *старта* контейнера,
а не готовности приложения внутри него. При любой гонке (например, `api`
ещё разворачивается или на секунду перезапускается) nginx стартовал раньше,
чем DNS-алиас `api` был доступен, падал с "host not found" и уходил в
рестарт-луп по `restart: always`. Исправлено двумя изменениями:

- `docker-compose.yml`: `nginx` теперь ждёт `api: condition: service_healthy`, а не просто "контейнер создан".
- `nginx/nginx.conf` и `nginx/nginx-ssl-example.conf`: `proxy_pass` резолвит `api` лениво на каждый запрос через `resolver 127.0.0.11 valid=10s;` вместо разового резолвинга при старте — так nginx переживает будущие перезапуски `api` без ручного `docker compose restart nginx`.

Применить: `docker compose up -d --build nginx` (пересоздаст nginx с новым конфигом и порядком запуска).

**2. Новый раздел админки «Синхронизация» (`/console/<uid>/sync`).**

Статус/история/настройки синхронизации с Ozon (включая отдельный контроль
скачивания фото), импорт цен с FTP-сервера с приоритетом над ценой Ozon, и
общая самопроверка — подробности в разделе
["Синхронизация с Ozon"](#синхронизация-с-ozon) выше. Добавлены новая таблица
`sync_settings`, новые колонки в `parts` (`ftp_price`, `ftp_price_updated_at`)
и `sync_log` (`source`) — применить миграции:

```
docker compose exec api alembic upgrade head
```

(поднимет базу с ревизии `0001` до `0003`; на уже существующей базе это
безопасно — только новые таблица/колонки, существующих данных миграции не
трогают). После этого пересобрать образ `api`/`sync_worker` — добавились
зависимости `openpyxl`/`xlrd` для чтения XLS/XLSX:

```
docker compose up -d --build api sync_worker
```

**3. Система авторизации с ролями** (`viewer`/`editor`/`full`) вместо
общего `ADMIN_TOKEN` — см. раздел [«Авторизация»](#авторизация) выше.

**4. Аудит безопасности перед продом.** Что нашли и сразу поправили:

- Логин (`/admin/auth/login`) не имел собственного лимита запросов — общий
  лимит 120/мин на все эндпоинты слишком мягкий для перебора пароля.
  Добавлен отдельный лимит 10/мин с одного IP на этот роут.
- Время ответа логина отличалось для существующего и несуществующего
  username (PBKDF2 считался только при найденном пользователе) — по этой
  разнице можно было перебором узнавать список логинов (тайминг-атака,
  CWE-208). Теперь PBKDF2 считается всегда, даже для неизвестного username
  (`verify_password_timing_safe` в `admin_auth.py`).
- Загрузка фото не отлавливала `Image.DecompressionBombError` Pillow
  ("картинка-бомба" — маленький файл, разворачивающийся в огромное число
  пикселей) — падала неконтролируемой 500-й ошибкой вместо чистого 400.
- В `nginx.conf` (обычный HTTP) не было базовых security-заголовков
  (`X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`) — раньше
  они были только в `nginx-ssl-example.conf`. Добавлены в оба конфига
  (HSTS остаётся только в SSL-варианте — по HTTP браузер его игнорирует).

Что проверили и **не** нашли проблем: SQL-инъекции (везде ORM с
параметризованными запросами), XSS через контент карточек/сайта (нигде не
используется `dangerouslySetInnerHTML`/`innerHTML`, React всегда экранирует
текст), обход загрузки файлов (реальный формат проверяется по содержимому
через Pillow, а не по имени/`Content-Type`, имена файлов — случайные UUID),
утечка секретов в репозиторий (`.env`, `backups/` в `.gitignore`), CORS
(закрыт по умолчанию, без `FRONTEND_ORIGIN` не пускает никого), доступ к
БД снаружи (порт `db` не пробрасывается на хост), права контейнера
(`api`/`sync_worker` работают от непривилегированного `appuser`).

Что стоит рассмотреть отдельно, не блокирует запуск: срок жизни сессии
администратора — 30 дней (можно сократить), `Content-Security-Policy`
header (имеет смысл добавлять вместе с HTTPS), сторонняя библиотека
`ozonapi-async` — нишевый пакет, стоит следить за обновлениями.

**5. Синхронизация больше не сохраняет чужие бренды продавца.** Раньше в
БД (и, соответственно, в админке — публичная витрина уже была отфильтрована)
попадал весь ассортимент продавца на Ozon, не только Omegation. Фильтр по
атрибуту 85 (бренд) теперь применяется в `sync_ozon.py` на этапе записи —
см. новый модуль `app/catalog_rules.py` и раздел [«Атрибуты Ozon и их роль в

пересобрать и перезапустить `api`/`sync_worker`:

```

  `ADMIN_URL_UID` — админка закрыта для всех. 8 неверных uid с одного IP за
  10 минут — бан IP на час.
- **Блокировка перебора пароля** (таблица `login_attempts`, миграция `0006`):
  10 неудач за 15 минут с одного IP — или по одному логину — блокируют вход (429),
  журнал: `docker compose exec api python manage_users.py login-log`.
- **Сессии** 12 ч / 2 ч простоя, не более 5 на пользователя, смена пароля и
  отключение закрывают все сессии пользователя. PBKDF2 — 600 000 итераций (старые
  хеши обновляются при входе). Пароли — от 12 символов.
- **Реальный IP посетителя** теперь доходит до приложения (раньше лимиты запросов
  считались по адресу контейнера nginx — один общий счётчик на всех).
- **nginx:** лимиты запросов и соединений, строгий лимит на вход (6/мин), таймауты,
  CSP и остальные заголовки, закрытые сканерам пути, `X-Forwarded-For` не
  принимается от клиента.
- **Docker:** БД в изолированной сети без выхода наружу и без секретов Ozon;
  `no-new-privileges`, `cap_drop: ALL`, лимиты процессов и логов.
- **FTP-настройки:** защита от SSRF (нельзя указать localhost/внутреннюю сеть/
  метаданные облака; частные сети — только при `OUTBOUND_ALLOW_PRIVATE=1`), потолок
  размера прайса 50 МБ.

### Применить на сервере
```
# 1. В .env добавить (см. .env.example):
#    ADMIN_URL_UID  -> openssl rand -hex 24
#    FTP_UPLOAD_PASSWORD, FTP_PUBLIC_IP
docker compose up -d --build
docker compose exec api alembic upgrade head      # новый сервер: alembic stamp head
cd frontend && npm install && npm run build && cd ..
docker compose restart nginx
docker compose exec api python manage_users.py admin-url   # покажет ссылку входа

```
Пароли существующих пользователей продолжают работать. Новые пароли и смена
пароля — от 12 символов.

### Встроенный FTP-сервер для прайсов
Контейнер `ftp` принимает **только FTPS** (шифрование обязательно) на порту 21 +
пассивный диапазон `FTP_PASV_PORTS` (откройте в файрволе; `harden-host.sh` делает
это). Логин `FTP_UPLOAD_USER` (по умолчанию `prices`), пароль `FTP_UPLOAD_PASSWORD`.
Разрешены только файлы `.csv`, `.xls`, `.xlsx`; скачивать, удалять и создавать
каталоги нельзя; хранятся последние 20 файлов.

В админке (Синхронизация -> Цены с FTP): **адрес сервера `local`**, путь к файлу —
имя файла или пусто (берётся самый свежий загруженный), включить импорт. Файл,
загруженный меньше 20 секунд назад, пропускается до следующего запуска.

Свой сертификат: положите `fullchain.pem` и `privkey.pem` в `./ftp-tls/` (владелец
uid 1000) и перезапустите `ftp`; без них создаётся самоподписанный — клиент один раз
подтверждает отпечаток. Пример загрузки: `curl --ssl-reqd -k -T prices.csv
ftp://prices:ПАРОЛЬ@<домен>/` (`-k` — только для самоподписанного).

### Если что-то пошло не так
- Забыли ссылку админки: `docker compose exec api python manage_users.py admin-url`.
- Заблокировали себя перебором: подождите 15 минут или удалите записи:
  `docker compose exec db psql -U $DB_USER -d $DB_NAME -c "DELETE FROM login_attempts"`.
- Не собирается образ из-за новых версий зависимостей (fastapi 0.115.6,
  python-multipart 0.0.20, Pillow 11.3.0, defusedxml, pyftpdlib, pyOpenSSL) —
  откатите номер версии в `app/requirements.txt` на прежний и пересоберите.
